# Assignment backlog database changes (local only)

The unpublished migrations are ordered after upstream's November 16 migrations: `202611160010_assignment_due_horizon.sql`, `202611160011_assignment_legacy_removal.sql`, and `202611160012_draft_oauth_restriction.sql`. The local runner creates a synthetic `assignments_draft` copy immediately before the upstream draft migration, which explicitly requires that table to exist. This is a test fixture, not evidence that any hosted environment has the expected table or structure.

The upstream draft migration replaces policies after the earlier MCP audit, leaving the draft table accessible to delegated OAuth tokens under its owner policy. The third migration adds the original restrictive OAuth policy to that table while preserving browser owner access. Its local tests cover populated owner drafts, cross-owner visibility, delegated read/insert/update/delete denial, and browser editing.

The due-date trigger checks newly inserted or changed non-null dates against one calendar year after the current Denver date, inclusive. PostgreSQL's calendar-year addition clamps February 29 to February 28 when needed. Unchanged legacy dates remain valid when editing other fields. Existing RPC wrappers, RLS, and private-core grants are unchanged; the trigger also covers direct table writes, AI confirmation, and MCP creation. Existing idempotent creation retries can still return their already-saved row.

A read-only schema inspection of the linked project found a cycle: deleting an assignment cascades to user_assignment, which cascades to the legacy user through assignment_user_id; Class_User can prevent that user deletion. Other assignments can also point at the same join row. The removal migration changes only those two nullable inbound references to ON DELETE SET NULL while preserving ON UPDATE CASCADE. It keeps the user, memberships, and unrelated assignments and allows the target's normal dependent rows to cascade. This changes the behavior for every deletion of a legacy user_assignment row, not only assignment removal, and deserves schema-owner review.

The local synthetic harness reconstructs the relevant legacy foreign keys and reproduces the reported Class_User error before migrations. It then verifies the fixed removal, preservation of linked records, access boundaries, and due-date paths. It does not establish the contents of hosted tables, inspect student records, or prove a hosted removal. Migrations have not been applied to the linked database. Before any live rollout, review the foreign-key effects and current schema, arrange the normal migration and recovery process, and separately authorize release; then verify using an appropriately approved synthetic account.
